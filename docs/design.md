# Jev가 Jstris에서 테트리스를 플레이하는 사이드 프로젝트

개발 스펙 v0.1 · 2026-09-18 · 구현 전 초안 · 현재 Jstris 상태 읽기 실측 반영

## 1. 만들 것

실제 Jstris 브라우저 화면에서 Jev가 블록의 착지 위치를 선택하고, 프로그램이 키보드로 그 위치까지 이동·회전·하드드롭하는 로컬 앱을 만든다. 사용자는 플레이를 보면서 선택한 위치, 다른 후보, 응답 시간, 사용 비용을 확인할 수 있다.

**핵심 설계: 블록 하나당 착지 후보를 한 번 평가한다.** 충돌·회전·도달 가능성·줄 삭제·구멍 개수는 코드가 계산한다. Jev는 실행 가능한 후보 중 하나를 선택한다. Jstris가 실제 게임 상태와 진행의 기준이다.

첫 완성 목표는 **Jstris 기본 규칙의 40줄 스프린트를 Jev 정책으로 완주하고, 그 과정을 기록으로 재검토할 수 있는 것**이다. Jev가 기존 테트리스 알고리즘보다 잘한다는 가설은 별도 비교 실험으로 평가한다. 구현 완료와 모델 우수성을 같은 판정으로 취급하지 않는다.

공개 소스 조사에 더해 현재 Jstris 1.40.1 비공개 연습방에서 상태 읽기와 이동·회전·하드드롭·홀드·재시작 입력을 직접 검증했다. [실측 기록](./jstris-live-state-verification.md)에 값과 제한을 정리했다. Jev API 연결과 자동 완주 실험은 수행하지 않았다. 아래 성능 수치는 측정 결과가 아닌 개발 목표다.

## 2. 범위와 기본 선택

로그인 프로필·공개 대전·순위 경쟁은 첫 버전의 범위에 넣지 않는다. 이는 사이드 프로젝트의 실험 환경 선택이다. 공식 안내는 비등록 사용자의 점수가 리더보드에서 제외된다고 설명한다.[S6] 페이지 URL뿐 아니라 실제 게임 모드를 읽어 싱글플레이인지 확인한다.

미포함: 화면 인식 AI, 멀티플레이 쓰레기 줄 대응, T-spin 최적화, 180도 회전, 소프트드롭 후 끼워넣기, 장기 탐색, 모델 학습, 배포 서비스, 사용자 계정, DB, 휴대폰 지원. 게임을 새로 만드는 것은 테스트용 규칙 시뮬레이터로 한정한다.

## 3. 오픈소스 조사와 적용 판단

확인 커밋: `86c8b24dd4cbf435380052b384919460b1215658`.[S1]

### 3.6 Jstris 기본 봇과 TBP

공식 v1.40 변경 기록에는 ColdClear·MisaMino 등의 브라우저 봇과 TBP 연동 방향이 있다.[S7][S8] 그러나 임의 외부 봇을 사용자가 등록할 수 있는 공개 인터페이스는 이번 조사에서 확인하지 못했다. TBP를 구현하면 곧바로 Jstris에 연결된다고 가정하지 않는다. v0.1은 관찰 어댑터+키보드로 시작하고, 정식 TBP 연결은 후속 조사로 둔다.

**재사용 원칙:** S1·S2·S3·S5의 확인한 체크아웃에서는 루트 LICENSE 파일을 찾지 못했다. 공개 열람과 재배포 허가는 구분한다. 이 스펙은 구조·관찰 결과를 참고하며 해당 코드를 복사·배포하는 것을 전제로 하지 않는다. 실제 편입 시 저장소 전체의 허가 조건을 별도로 확인한다.

## 4. Jstris 연결 가능성: 첫 개발 단계의 통과 조건

현재 화면에서 연습·스프린트·봇 메뉴와 v1.40.1을 확인했다. `/play/practice`는 조사 당시 `/?play=2`로 이동했다. 이 값 하나를 게임 모드 판정에 사용하지 않는다.

현재 내려오는 공개 `game.js`는 난독화돼 있지만, 런타임의 `Game.prototype.redraw`는 접근 가능하다. 원래 메서드를 보존하는 관찰 래퍼에서 `this`를 잡아 20×10 `matrix`, `activeBlock`, `queue`, `blockInHold`, `holdUsedAlready`, `placedBlocks`를 읽었다. 좌 이동(x 3→2), 회전(rot 0→1), 하드드롭(고정 셀 4개 추가·다음 블록 생성), 홀드와 재시작까지 직접 확인했다. `window.game`은 원래 없으므로 별도 포착이 필요하다. [실측 기록](./jstris-live-state-verification.md).

**확인된 주의점:** 보드 셀 값은 종류 ID와 다른 색상 코드다. 재시작에서도 인스턴스는 유지되며 준비 화면에는 이전 보드가 잠시 남는다. `starting`·`play`·`gameEnded`를 함께 고려하고 별도 gameEpoch를 관리한다. 스폰 직후 활성 블록의 y=-2를 관찰했지만 숨겨진 고정 셀, top-out, 줄 삭제 및 완전한 생명주기 계약은 아직 확인하지 않았다. 따라서 아래 M0의 남은 검증을 완료한 뒤 Jev를 연결한다.

1. 전용 비로그인 Chromium을 연습 모드로 연다. 개인 브라우저 프로필을 붙이지 않는다.
2. 게임 객체를 찾을 수 있는 읽기 경로를 조사한다. 필요하면 알려진 렌더/생성 지점에 원래 반환값·예외·호출 횟수를 보존하는 얇은 관찰 훅을 붙인다.
3. 고정 블록, 활성 블록, 회전·위치, 홀드, 보이는 다음 큐, 모드, 시작·종료·줄 삭제 상태를 한 번의 페이지 작업으로 복사한다.
4. 연속 동일 종류 블록도 구분할 spawn/lock 이벤트 또는 단조 증가 카운터를 확보한다. 모양 ID나 보드 해시만으로 블록 생성을 판정하지 않는다.
5. 빈 보드, 일반 적층, 한 줄 삭제, 높은 적층에서 화면과 스냅샷을 대조한다. 숨겨진 위쪽 행, 좌표 원점, 조각 ID 매핑도 확인한다.
6. 각 키의 keydown/keyup 한 쌍이 의도한 단일 행동인지 확인하고, 좌·우/회전/하드드롭 이후 실제 상태를 읽는다.

완료 증거: `adapter-contract.json`, 필드 대응표, 클라이언트 자산 지문, 10개 이상의 관찰 사례, 수동 입력 전후 비교 기록. 상태·규칙·생명주기 중 하나라도 식별할 수 없으면 자동 플레이 단계로 넘어가지 않는다.

이 단계는 **집중 개발 0.5~1일을 배정한 조사 단계**다. 실패하면 불명확한 필드를 추측하지 않고, 화면 인식 어댑터로 범위를 변경할지 결정한다. 자체 테트리스로 바꿔 Jstris 구현 완료라고 보고하지 않는다.

## 5. 시스템 구성

```text
Jstris 전용 브라우저
  ├─ 상태 관찰 ──→ JstrisAdapter ──→ Snapshot
  │                                  ↓
  │                     규칙·도달 경로·착지 후보 계산
  │                                  ↓
  │                      JevPolicy / BaselinePolicy
  │                                  ↓
  └─ 키 입력 ←── Executor ←── 최신 상태에서 재검증
                       ↓
                 착지 결과 대조
                       ↓
                JSONL 기록 + 콘솔 패널
```

Node 프로세스 하나가 브라우저 수명, 모델 요청, 실행, 기록을 소유한다. 상태 관찰·모델 호출·키 입력을 여러 프로세스로 나누지 않는다. 패널은 별도 로컬 페이지지만 같은 프로세스가 제공하며, 게임 실행 권한은 Runner에만 둔다.

| 모듈 | 책임 |
|---|---|
| `jstris-adapter` | 현재 클라이언트와 정규화 Snapshot 사이의 변환, 모드/규칙 확인, 키 전송 |
| `rules` | 조각 형태, 충돌, 90도 회전과 킥, 하드드롭, 줄 삭제, top-out 판정 |
| `placements` | 현재 포즈에서 도달 가능한 착지와 키 경로 계산, 결과 특징 측정 |
| `jev-policy` | 후보를 Choice 질문으로 전송, 응답 구조·후보 ID 확인 |
| `baseline-policy` | 동일 후보에 대해 고정 휴리스틱 또는 seeded random 선택 |
| `runner` | 한 블록의 요청·실행 수명, 취소, 재검증, 종료 |
| `recorder` | 원본 입력·응답·실행 경로·실제 결과·비용 기록 |
| `console` | 상태, 실행/중단, 선택 후보, 지연·비용·결과 표시 |

폴더는 `src/` 아래 위 모듈별로 나누고 `tests/fixtures`, `runs/`를 둔다. 작은 단일 패키지로 시작한다. 모델 키는 Node 환경변수 `TYPESAFE_API_KEY`로만 읽는다. Jstris 페이지·패널 JavaScript·로그에는 키를 전달하지 않는다.

브라우저는 Playwright로 직접 관리한다. 어댑터 내부 필드 접근은 조사에서 확인한 경로만 사용하고, 프로그램이 고정 블록·활성 좌표·난수 큐를 직접 변경하지 않는다.

## 6. 데이터 계약

### 6.1 Snapshot

```ts
type Piece = "I" | "O" | "T" | "S" | "Z" | "J" | "L";
type Rotation = "0" | "R" | "2" | "L";

interface Snapshot {
  runId: string;
  gameEpoch: number;       // 재시작마다 증가
  pieceSeq: number;        // 활성 블록 생성마다 증가; 같은 종류도 별개
  observedAtMs: number;    // Runner의 단조 시간 기준
  boardRevision: number;   // 고정 보드 변경 시 증가
  poseRevision: number;    // 이동/회전/중력 변경 시 증가
  ruleProfileId: string;
  phase: "waiting" | "active" | "clearing" | "finished";
  mode: "practice" | "sprint40";
  board: number[][];       // 고정 셀만. ghost/활성 블록 제외
  minY: number;            // 숨겨진 행을 포함하는 최소 y
  active: { kind: Piece; rotation: Rotation; x: number; y: number } | null;
  nextVisible: Piece[];    // 화면에 공개된 미리보기까지만
  hold: Piece | null;
  holdAvailable: boolean;
  lines: number;
  lockedPieces: number;
}
```

화면의 왼쪽 열은 x=0, 보이는 맨 위 행은 y=0, 아래쪽으로 y가 증가한다. 보드 폭은 기본 모드에서 10을 기대하되 실제 검증한다. 숨겨진 행은 음수 y로 표현하고 배열 인덱스는 `y - minY`로 변환한다. 활성 조각의 회전 원점과 착지 셀의 최소 x/y는 별개 필드로 취급한다.

`ruleProfileId`에는 보드 치수, 조각·회전·킥, 스폰 위치, 중력·lock delay, 줄 삭제 지연, 키 매핑, 지원 모드와 클라이언트 지문을 묶는다. Jstris 기본 규칙에 대응하는 실제 검증 자료로 작성한다. 일반 SRS라는 명칭만으로 일치했다고 판단하지 않는다.

### 6.2 Placement

```ts
interface Placement {
  id: string;                    // 해당 요청에서만 유효한 opaque ID
  occupiedCells: [number, number][]; // 줄 삭제 전 고정될 네 셀
  rotation: Rotation;
  path: ("left" | "right" | "cw" | "ccw" | "hardDrop")[];
  afterBoardHash: string;         // 줄 삭제까지 적용한 결과
  features: {
    clearedLines: number;
    holesAfter: number;
    holesDelta: number;
    aggregateHeightAfter: number;
    maxHeightAfter: number;
    bumpinessAfter: number;
    topOut: boolean;
  };
}
```

구멍은 같은 열에서 위에 고정 셀이 있는 빈 셀 수, 높이는 바닥부터 최상단 고정 셀까지의 높이, 굴곡은 인접 열 높이 차의 절댓값 합이다. 모든 결과 특징은 줄 삭제 후 보드에서 계산한다. 숨겨진 행도 충돌·높이·top-out 처리에서 버리지 않는다.

## 7. 후보 생성: 실행 가능성과 좋은 수를 분리한다

1. 최신 활성 포즈를 시작점으로 좌·우·90도 회전 상태를 탐색한다. 회전 킥에 의한 y 이동도 상태에 포함한다.
2. 각 도달 포즈에서 하드드롭을 시뮬레이션해 최종 네 셀과 입력 경로를 얻는다.
3. 충돌·범위 초과·현재 규칙의 top-out 후보를 제거하고, 같은 최종 셀은 가장 짧은 경로로 합친다.
4. 후보마다 줄 삭제와 보드 특징을 코드로 계산한다. 구멍이 생긴다는 이유만으로 후보를 제거하지 않는다.
5. v0.1은 소프트드롭 후 이동·회전으로 들어가는 배치를 탐색하지 않는다. 즉, 후보 목록은 **지원 입력으로 도달 가능한 배치 집합**이지 모든 테트리스 합법 수의 완전한 목록이 아니다.
6. 후보가 0개면 `NO_SUPPORTED_PLACEMENT`로 종료한다. Jstris의 실제 top-out과 구분한다.
7. Choice 최대 255개를 지킨다.[S9] 초과 시 조용히 상위 후보를 자르지 않고 입력 범위 오류로 중단한다. 확장 때 계층적 선택 또는 명시적 후보 제한 실험을 추가한다.

Jev 호출 전에 계산한 경로는 시간 경과 후 그대로 신뢰하지 않는다. 중력이 진행되므로 응답 수신 후 현재 포즈에서 **동일한 네 셀로 가는 경로를 다시 계산**한다. 키 입력 후에도 다음 입력의 전제 상태를 확인한다.

## 8. Jev 요청과 선택 정책

직접 HTTP `POST https://api.typesafe.ai/v1/systemone`를 사용한다. 작은 fetch 래퍼에 timeout·응답 검증·토큰 계측을 모아 SDK 자동 재시도가 게임 지연을 늘리지 않도록 한다. 영어 지시문, 한국어 UI를 사용한다.[S10]

한 요청에는 `placement` Choice 질문 하나를 둔다. 회전·열·홀드를 독립 질문으로 분리하면 서로 결합할 수 없는 답이 나올 수 있으므로, 완성된 후보 ID 하나를 선택하게 한다.

요청의 개념 구조:

```json
{
  "model": "jev-1.13.0",
  "state": {
    "objective": "Finish the 40-line sprint without topping out.",
    "currentPiece": "T",
    "nextVisible": ["I", "L", "O"],
    "linesRemaining": 28,
    "currentFeatures": {"holes": 1, "maxHeight": 7}
  },
  "questions": {
    "placement": {
      "type": "choice",
      "instructions": "Choose one reachable placement. Prioritize survival, avoiding buried empty cells, and clearing lines while keeping the stack manageable. The supplied consequences are already computed; do not recalculate geometry.",
      "criteria": {
        "p_a": {"clearedLines": 1, "holesAfter": 0, "holesDelta": -1, "maxHeightAfter": 6, "aggregateHeightAfter": 30, "bumpinessAfter": 8},
        "p_b": {"clearedLines": 0, "holesAfter": 1, "holesDelta": 0, "maxHeightAfter": 7, "aggregateHeightAfter": 40, "bumpinessAfter": 6}
      }
    }
  }
}
```

위 숫자는 형식 설명용이며, fixture에서 측정한 값이 아니다.

구현에서는 후보별 회전·최소 점유 열과 코드가 계산한 짧은 결과 설명을 더한다. 큰 보드 문자열, 후보별 보드 전체, 아직 공개되지 않은 미래 블록은 보내지 않는다. 정확한 계산을 코드에 두라는 공식 지침을 따른다.[S11]

기본 실험에서는 `bestPlan`, `recommended`, 종합 점수, 휴리스틱 순위를 입력하지 않는다. 후보는 로그에 기록된 seed로 순서를 섞고 opaque ID를 붙인다. 후보 ID와 키 경로의 대응은 Runner가 보관한다. 실제 API 응답의 선택 ID·확률 분포·confidence·resolved model·토큰 사용량을 원형으로 저장한다.

`confidence`와 선택 후보의 확률은 분리해 표시한다. 둘 다 완주 확률이나 승률로 표시하지 않는다. v0.1은 confidence 임계값을 임의로 정해 수를 대체하지 않고, 유효하고 최신 상태에서도 실행 가능한 선택을 수행한다. 낮은 confidence는 분석용 표시만 한다.

API 키 없음·권한 오류는 시작 전 표시한다. Jev로 시작했는데 키가 없다고 로컬 봇을 실행하지 않는다. 휴리스틱과 랜덤은 사용자가 별도로 선택하는 평가 모드다.

## 9. 실행 루프와 실패 처리

```text
IDLE → READY → OBSERVING → REQUESTING → REVALIDATING
                                      ↓
                                 EXECUTING → VERIFYING → OBSERVING
어느 단계든: 중단/종료/오류 → STOPPING → FINISHED 또는 ABORTED
```

정상 루프:

1. 관찰 상태가 `active`이고 지원 모드·규칙인지 확인한다.
2. `{gameEpoch, pieceSeq, boardRevision, ruleProfileId}`와 함께 후보 집합을 고정한다.
3. 한 번의 Jev 요청을 전송한다. 대기 중 새 블록·리셋·종료 이벤트를 관찰하고 이전 요청은 무효화한다.
4. 응답이 오면 요청 ID 및 위 식별자를 대조한다. 동일 종류의 다음 블록에도 이전 응답을 적용하지 않는다.
5. 중력에 따른 pose 변화만 있으면 목표 셀을 유지한 채 경로를 재탐색한다. 목표 도달이 불가능하면 해당 결정을 폐기한다.
6. 키 입력을 한 번씩 전송한다. 누름/떼기를 `finally`로 보장한다. 한꺼번에 긴 문자열을 보내지 않는다.
7. 하드드롭 직전 최신 활성 포즈·착지 셀을 다시 확인한다. 한 pieceSeq에 하드드롭은 최대 한 번만 보낸다.
8. lock·줄 삭제·다음 spawn 이후 고정 보드, 줄 수 증가, 블록 수 증가를 예상값과 대조한다.
9. 일치한 결과를 저장한 뒤 다음 블록으로 진행한다.

| 상황 | 처리 |
|---|---|
| 요청 timeout·429·5xx | 기본은 해당 게임의 봇 입력 중단, 실패 기록. 자동 HTTP 재시도 없음 |
| 응답 중 블록이 바뀜/리셋 | 응답 폐기; 진행 중인 실행도 취소하고 종료 사유 기록 |
| 같은 블록인데 목표에 못 감 | 측정된 남은 제어 시간이 충분할 때만 새 상태로 최대 1회 재질문. 그렇지 않으면 중단 |
| 알 수 없는 후보/잘못된 응답 | 프로토콜 오류로 중단. 임의의 후보 선택 없음 |
| 키 입력 결과 불일치 | 후속 키를 멈추고 상태를 읽음. 새 pose에서 같은 목표로 재계획 가능한 경우만 계속 |
| 착지 후 보드 불일치 | `DESYNC`로 중단하고 전후 Snapshot·경로·스크린샷 저장 |
| 사용자 조작·창 포커스 상실 | 모든 키를 떼고 요청/실행 취소; 수동 Resume 전에는 다시 입력하지 않음 |
| 페이지 이동·탭 종료·브라우저 종료 | 요청 취소, 키 정리, 실행 종료 |
| 취소와 하드드롭 경합 | 아직 미전송된 입력은 차단. 이미 전송된 입력은 되돌리지 않고 최종 관찰에 기록 |

**중단은 봇 입력의 중단이다.** Jstris 게임이 자동으로 일시정지됐다고 표시하지 않는다. 게임 자체는 정상 중력으로 계속 진행할 수 있다. Resume은 최신 상태로 새 결정부터 시작하며 중간 키 배열을 이어 보내지 않는다.

v0.1 timeout 시작값은 1,000ms, 실행 확인 500ms, 착지 확인 2,000ms로 둔다. 모두 설정값이며 첫 연결 측정 뒤 조정한다. deadline은 가능하면 실제 낙하·lock 상태에서 계산한 남은 시간에서 측정한 실행 p95와 여유 시간을 뺀 값으로 더 짧게 제한한다. 남은 시간을 검증할 수 없으면 재질문을 허용하지 않는다.

## 10. 화면과 사용자 흐름

1. 로컬 앱을 시작하면 전용 Jstris 탭과 콘솔이 열린다.
2. 상태 패널에 `연결 확인 중 → 연습 준비됨`이 표시된다. 지원되지 않는 클라이언트면 원인을 표시한다.
3. 정책을 `Jev / 휴리스틱 / 랜덤` 중 선택한다. 실행 중 정책을 바꾸려면 현재 실험을 끝내고 새 run을 만든다.
4. `시작`은 준비된 싱글플레이 게임을 시작하고 봇을 실행한다. `중단`은 즉시 봇 입력을 멈춘다. 시작 전에는 어떠한 게임 입력도 보내지 않는다.
5. 게임 영역 옆에 마지막 착지 후보와 상위 대안 3개, confidence, 응답 지연, 누적 줄 수·PPS·비용을 표시한다. Jev가 설명을 생성한 것처럼 이유 문장을 만들지 않고 계산된 결과를 보여준다.
6. 종료 후 완주/실제 top-out/지원 후보 없음/연결 오류/사용자 중단을 구분하고 기록 폴더를 보여준다.

Jstris 탭의 포커스를 빼앗지 않도록 실행 중 패널은 관찰용이다. 패널에서 중단을 누르면 게임 포커스가 사라져도 중단이 성립해야 한다. `한 수 실행`은 최신 상태에서 한 블록을 처리한 뒤 봇을 멈춘다. 이때도 게임을 동결하지 않는다.

콘솔 서버는 loopback에만 바인딩하고 실행마다 세션 토큰을 발급한다. 제어 요청은 같은 origin과 토큰을 확인한다. Jstris 페이지에서 임의의 로컬 API를 부르게 하지 않고 Node가 모델 호출을 소유한다.

## 11. 측정과 Jev 기여도 평가

### 실행별 저장

`runs/<runId>/manifest.json`, `decisions.jsonl`, `summary.json`, 오류 스크린샷을 저장한다. manifest에는 git SHA, Node/브라우저 버전, Jstris 자산 지문, rule profile, 정책 버전, 프롬프트 해시, 요청한 모델과 응답 모델, 설정, 시작·종료 시간을 담는다.

결정 로그에는 요청 당시 Snapshot, 후보 전체와 순서, 선택, 확률·confidence, 재검증 당시 Snapshot, 실제 키 이벤트, 착지 후 상태, 각 구간 시간, 폐기·재질문 사유를 담는다. 프롬프트와 입력은 파일로 보관하되 API 키·쿠키·채팅·다른 플레이어 데이터는 수집하지 않는다.

### 비교군

| 정책 | 역할 |
|---|---|
| Jev | 동일 후보와 특징만 받아 선택하는 주 실험 |
| 고정 휴리스틱 | 같은 특징을 고정 규칙으로 정렬하는 비교군 |
| Seeded random | 지원 후보 중 무작위 선택하는 최소 비교군 |

초기 휴리스틱은 `(holesAfter, -clearedLines, maxHeightAfter, aggregateHeightAfter, bumpinessAfter, pathLength)`를 오름차순 사전식으로 비교한다. 가중치 최적화 없이 읽기 쉬운 기준으로 시작한다. 후보 생성·키 실행·규칙은 세 정책에서 공유한다.

개발용 fixture와 평가용 fixture를 분리한다. 오프라인에서는 고정 seed의 7-bag 게임으로 같은 시작 조건을 재현하되, 자체 엔진 결과와 Jstris 실측을 분리해 보고한다. Jstris에 동일 seed 설정이 검증되지 않으면 각 live run을 동일 시드 비교라고 부르지 않는다. 과거 결정 Snapshot을 다른 정책에 다시 묻는 실험은 선택 비교이며, 반사실적 전체 게임 성적이 아니다.

보고 항목: 40줄 완주율, 실제 top-out 비율, 지원 후보 없음 비율, 연결/실행 실패율, 완료한 줄·블록, 최대 높이·구멍, 게임 벽시계 시간, 실제 lock 기반 PPS, 요청/블록, 폐기율, 재질문율, Jev/전체 지연 p50·p95, 실제 input tokens·예상 비용. 실패 run도 전부 분모에 포함한다.

별도 실험으로만 추천 점수 노출 또는 깊이 1 lookahead를 추가한다. 이런 실행은 `Jev+planner`로 표시해 기본 Jev 결과와 섞지 않는다.

## 12. 성능·비용 목표

초기 데모 목표는 실제 벽시계 기준 **평균 1 PPS 이상**, Jev 지연 p95 800ms 이하, 관찰부터 착지 확인까지 p95 1,200ms 이하이다. 한국에서의 API 지연과 Jstris 지연에 따라 조정한다. 이를 위해 게임을 느리게 하거나 대기 시간을 영상에서 빼지 않는다.

공식 문서의 현재 단가는 입력 100만 토큰당 $0.042, 출력 무료다. 현재 문서의 요청 제한은 분당 1,200회이지만 변동 가능하므로 응답과 계정 제한을 우선한다.[S10]

예상 비용 계산: `전체 input_tokens × 0.042 / 1,000,000`.

| 가정 | 계산상 모델 비용 |
|---|---:|
| 요청당 3,000 input tokens | $0.000126 |
| 1,000블록 × 블록당 1회 | $0.126 |
| 1 PPS로 1시간, 같은 입력 크기 | 약 $0.454 |

숫자는 예산 예시다. 후보 수·문장 길이·재질문에 따라 달라진다. 토큰 수를 문자 수로 확정하지 않고 API usage를 누적한다. 초기 로컬 예산은 run당 $0.25 또는 1,000결정 중 먼저 도달한 조건으로 중단한다. 응답이 없어 사용량이 누락된 호출은 과금 0으로 단정하지 않고 별도 표시한다. 이 문서는 유료 호출을 실제 실행하지 않는다.

## 13. 개발 순서와 완료 기준

### M0 — 현재 Jstris 연결 계약 확보 · 예상 0.5~1일

기본 인스턴스 포착·상태 읽기·이동/회전/하드드롭·홀드·재시작은 실측했다. 남은 줄 삭제·높은 적층·생성/고정 이벤트·규칙 계약과 4절의 증거를 완성한다. M0 전체가 완료된 것은 아니다.

### M1 — 규칙과 입력 실행 검증 · 예상 1~2일

Jev 없이 고정 후보를 선택해 연습 모드에서 놓는다. 규칙 fixture와 현재 Jstris의 결과가 일치해야 한다. 후보는 실제 경로를 가지며 좌표 직접 적용을 하지 않는다.

### M2 — Jev 연결과 40줄 루프 · 예상 1~2일

Choice 요청, 버전 고정, 취소·재검증·실패 기록을 붙인다. 기본 모드에 묵시적 fallback이 없고, 모델 응답이 실제 키 실행과 연결되는지 확인한다.

### M3 — 관찰 패널과 비교 실험 · 예상 1일

결정·대안·지연·비용 표시와 실행 요약을 완성한다. 휴리스틱/랜덤과 동일한 실행 경로를 사용한다. 기대 총량은 연결 조사 성공 시 집중 개발 3.5~6일이며, 상태 접근이나 규칙 불일치가 크면 늘어난다.

| ID | 수용 기준 | 검증 방식 |
|---|---|---|
| AC-01 | 실제 Jstris 기본 40줄 스프린트에서 동작 | URL·mode·화면·클라이언트 지문 포함 실행 기록 |
| AC-02 | 관찰 보드와 Jstris 화면/게임 상태 일치 | 빈 보드·일반 적층·줄 삭제·숨겨진 행 fixture |
| AC-03 | 7종 조각·벽 회전·막힌 이동·1~4줄 삭제·스폰/lock-out 처리 | 순수 규칙 테스트와 대표 Jstris 대조 사례 |
| AC-04 | 모든 제공 후보에 유효한 입력 경로와 예측 결과 존재 | 후보별 replay property test, 무효 경로는 API 전달 전 제거 |
| AC-05 | 실제로 보낸 키와 착지 결과 일치 | 여러 게임에 걸친 누적 200회 배치의 보드 대조, 불일치 0건; 정책 실력과 분리 |
| AC-06 | stale 응답·재시작·동일 조각 연속·중단 경합에서 이전 응답을 실행하지 않음 | 지연 API 대역과 브라우저 통합 테스트 |
| AC-07 | Jev 모드에서 모든 정책 선택 출처가 Jev 또는 명시적 단일후보 처리 | 로그 대조; 대체 알고리즘 0회 |
| AC-08 | timeout·429·탭 종료·포커스 상실·착지 불일치에서 제어된 종료 | 오류 주입 및 키 해제 확인 |
| AC-09 | Jev로 40줄 스프린트 최소 1회 완주 | 연속 실행 영상과 전체 JSONL; 실패 시 모델 목표 미달로 명시 |
| AC-10 | 고정 설정으로 Jev 평가 20게임 수행, 최소 16게임 완주 목표 | 모든 시도와 중단 이유 포함; 목표 미달도 결과로 보고 |
| AC-11 | 실제 API usage·모델 버전·latency를 관찰 가능 | 원응답과 요약의 집계 대조 |
| AC-12 | API 키가 브라우저·기록에 포함되지 않음 | 요청 경로와 산출물 검사 |

후보가 정확히 하나일 때는 모델 선택 여지가 없으므로 API를 생략할 수 있다. 이 경우 `decisionSource=singleCandidate`와 호출 생략을 명시하고, “모든 블록에 Jev를 호출했다”고 보고하지 않는다.

기능 수용은 AC-01~09 및 AC-11~12를 기준으로 한다. AC-10의 완주율·성능 목표는 모델 품질 지표다. 기능이 완성됐어도 목표를 못 맞추면 설정·특징·전략을 개선할 후속 작업으로 남긴다. 휴리스틱보다 못해도 결과를 숨기지 않는다.

## 14. 후속 확장

1. **홀드:** 후보에 `useHold`를 포함한 완성 배치를 추가한다. 빈 홀드가 다음 큐를 소비하는 경우와 한 블록당 1회 제한을 검증하고, 실제 홀드 후 상태가 예상과 맞는지 확인한 다음 이동한다.
2. **더 넓은 도달 탐색:** 소프트드롭·끼워넣기·T-spin 경로를 지원한다. lock delay와 입력 시간이 포함된 탐색이 필요하다.
3. **봇 대전:** Jstris 내장 봇에 대한 입력 측 연동과 정식 TBP 연결을 비교 조사한다. 쓰레기 줄 수신·상쇄·대기 큐가 추가되므로 스프린트 어댑터를 그대로 사용하지 않는다.
4. **전략 비교:** 순수 특징 입력, 휴리스틱 힌트 제공, lookahead 제공을 분리해 Jev의 기여도를 측정한다.

## 15. 초안의 가정과 남은 확인

**현재 기본 선택:** 먼저 혼자 플레이하는 40줄 스프린트를 완성하고, 한 블록의 착지는 Jev가 고르며 이동 키는 코드가 결정한다. 이 선택으로 전체 스펙을 작성했으며 대답을 기다리느라 구조를 미완성으로 두지 않았다.

제품 방향상 확인할 질문은 두 가지다.

- 첫 목표가 “Jev가 Jstris를 플레이하는 모습을 관찰”하는 것인지, “ColdClear 같은 봇과 대전”까지 포함하는지. 초안은 전자를 택했다.
- Jev가 매 키 입력을 고르는 데 의미를 두는지, 착지 위치를 고르고 코드는 실행하는 방식이면 되는지. 초안은 완주와 비교가 쉬운 후자를 택했다.

기술적으로 미확정인 부분은 개발자가 M0 및 연결 단계에서 확인한다: 이벤트와 hidden-row 계약, 실제 회전·스폰·lock 규칙, 키 입력 최소 간격, 해당 계정의 API 접근 권한과 지역 지연. 현재 인스턴스 접근 경로는 실측으로 확인했다. 이는 사용자에게 구현 방식을 대신 결정해 달라고 묻는 항목이 아니다.
